# hexrl-platform

Это сервис для интерактивного взаимодействия пользователей с RL и для наглядного обучения тому, как работают алгоритмы RL


## Quick start

Нужно установить [uv](https://docs.astral.sh/uv/getting-started/)
```
git clone https://github.com/mematvey/hexrl-platform.git
cd ./hexrl-platform
uv sync
```

## MLflow

MLflow хранит метаданные экспериментов и версий моделей в отдельной базе PostgreSQL,
а файлы запусков и моделей — в S3-совместимом RustFS. Сам Tracking Server принимает
запросы клиентов и отдаёт веб-интерфейс. Данные обоих хранилищ переживают перезапуск
контейнеров благодаря отдельным Docker volumes.

Скопируйте `.env.example` в `.env`, задайте собственные пароли и ключи. Затем запустите:

```bash
docker compose up -d --build mlflow
docker compose ps
```

После запуска интерфейс доступен на `http://localhost:5000` (или на порту `MLFLOW_PORT`).
Tracking API доступен там же. Для локальных экспериментов задайте
`MLFLOW_TRACKING_URI=http://127.0.0.1:5000`. Внутри Compose адрес сервера —
`http://mlflow:5000`. Порт публикуется только на локальной машине; для общего
доступа нужны отдельные аутентификация и TLS.

В `mlflow-db` хранятся эксперименты, запуски, параметры, метрики и записи Model
Registry. В `artifact-store` хранятся большие файлы — графики, датасеты и модели.
Контейнер `artifact-bucket` создаёт бакет при первом запуске и ничего не меняет,
если он уже существует. Данные удаляются только при явном удалении volumes.

## Реплеи и EDA

Первый сценарий среды — навигация к цели по гексагональной карте. Координаты заданы
двумя осями `q, r`; действия `0..5` соответствуют шести соседним клеткам.
Препятствия не позволяют пройти через клетку, но попытка хода всё равно расходует
шаг. Эпизод заканчивается при достижении цели или исчерпании лимита шагов.
Карта, награды и лимит задаются параметрами среды. Формат реплея версионируется:
при добавлении новых наблюдений или игровых механик схему можно расширять явно.

Подготовьте окружение для экспериментов и сгенерируйте реплеи:

```bash
uv sync --group experiments
uv run --group experiments hexrl-generate-replays --episodes 1000 --seed 42
uv run --group experiments hexrl-eda
```

Генератор создаёт `data/replays/navigation.jsonl` — по одной записи на переход,
включая наблюдение до и после действия, действие, награду, признак завершения,
поведенческую политику и вероятность выбранного действия. Рядом появляется
`navigation.manifest.json`: версия схемы и симулятора, карта, параметры генерации,
число эпизодов и SHA-256 исходного файла. При одинаковых параметрах и seed байты
реплея и его digest совпадают. Выходные файлы не попадают в Git.

По умолчанию политика каждого эпизода выбирается с вероятностью 50/50: равномерно
случайные действия либо движение по кратчайшему маршруту с 25% вероятностью
равномерного исследовательского выбора.
Это политики *сбора данных*, а не обученные модели. Анализ проверяет SHA-256,
считает долю успешных эпизодов, среднюю награду, длину эпизода и частоту ходов
в препятствие, затем сохраняет в MLflow графики длины эпизодов, успешности в
зависимости от расстояния до цели и посещаемости клеток.

В MLflow входной dataset имеет `source` типа `code`: датасет синтетический, поэтому
его происхождение — генератор (`generated://hexrl/navigation`, функция, версия
симулятора и seed), а не путь к файлу на чьём-то диске. Также у него есть `digest`
(первые 32 символа SHA-256) и контекст `analysis`. Полный SHA-256 хранится в manifest и теге run:
MLflow ограничивает длину поля `digest`. Сам JSONL и manifest дополнительно
сохранены как артефакты run. Параметры генератора и версия симулятора показывают
происхождение данных (`lineage`). По умолчанию команда обращается к
`http://127.0.0.1:5000`; для другого адреса используйте `--tracking-uri` или
переменную `MLFLOW_TRACKING_URI`.

## Эндпоинты

Swagger доступен на `/docs` после запуска приложения

### `GET /healthz`

Быстрая проверка, что процесс жив и отвечает на запросы. Никуда не ходит: ни в базу, ни в другие сервисы

Путь без префикса `/api/v1` осознанный. Это инфраструктурная ручка, а не часть версионируемого API

Пример ответа (`200 OK`):

```json
{"status": "ok"}
```

### `GET /api/v1/version`

Возвращает имя и версию приложения. Версия читается из метаданных установленного пакета, то есть из `pyproject.toml`. В коде она нигде не продублирована

Пример ответа (`200 OK`):

```json
{"name": "hexrl-platform", "version": "0.2.0"}
```

### `GET /api/v1/health`

Сквозная проверка (end-to-end): приложение реально обращается к зависимостям и сообщает, что с ними происходит. Для каждого компонента возвращаются статус, версия и время ответа

Каждая проверка ограничена по времени (`HEALTH_TIMEOUT_SECONDS`, по умолчанию 2 секунды), поэтому зависшая зависимость не подвесит сам запрос

Поля ответа:

| Поле | Описание |
| --- | --- |
| `status` | Общее состояние: `ok`, если все компоненты работают, иначе `degraded` |
| `component.name` | Название компонента (сейчас `postgres`) |
| `component.status` | `up` или `down` |
| `component.version` | Версия компонента, `null` если проверка не прошла |
| `component.latency_ms` | Время ответа компонента в миллисекундах |
| `component.error` | Тип ошибки, если компонент недоступен, иначе `null` |

Если хотя бы один компонент недоступен, ответ приходит со статусом `503 Service Unavailable`, чтобы мониторинг и оркестратор могли отреагировать по коду ответа, не разбирая тело

Пример ответа (`200 OK`):

```json
{
  "status": "ok",
  "components": [
    {
      "name": "postgres",
      "status": "up",
      "version": "PostgreSQL 16.4 on x86_64-pc-linux-gnu",
      "latency_ms": 3.12,
      "error": null
    }
  ]
}
```

Пример ответа, когда база недоступна (`503`):

```json
{
  "status": "degraded",
  "components": [
    {
      "name": "postgres",
      "status": "down",
      "version": null,
      "latency_ms": 452.06,
      "error": "InvalidPasswordError"
    }
  ]
}
```

## Логирование

Приложение пишет в stdout по одной JSON-записи на строку. У каждой записи есть время в UTC,
уровень, имя логгера, событие, имя и версия сервиса. События HTTP-запросов содержат метод,
путь, код ответа, длительность и `request_id`. Этот идентификатор возвращается клиенту в
заголовке `X-Request-ID` и связывает запрос с проверкой PostgreSQL. В логах проверки компонента
есть его имя, длительность и версия либо тип ошибки; пароль и строка подключения не выводятся.

Уровень задаётся переменной `LOG_LEVEL` в `.env` (по умолчанию `INFO`). Логи контейнера можно
посмотреть командой `docker compose logs -f app`.

Пример записи:

```json
{"timestamp":"2026-09-27T12:00:00.000Z","level":"INFO","logger":"hexrl_platform.main","event":"http_request_completed","service":"hexrl-platform","service_version":"0.2.0","request_id":"e4c9","method":"GET","path":"/healthz","status_code":200,"duration_ms":1.5}
```
